# ECRS2021 - Change Log (September 25, 2026)

**Date:** September 25, 2026

This document summarizes the changes made to the `ECRS2021` repository on
September 25, 2026: enabling multithreaded (parallel) simulation, tidying up
idle files, and a thread-safety change in the shared field header.

| Commit | Summary |
|--------|---------|
| `f14cd63` | Parallelize ECRS simulation with Geant4 event-level multithreading |
| `ddefbb2` | Remove idle/junk files (`.DS_Store` and dead CVS metadata) |
| `6b760ba` | Declare `where_in_magnetopause2001__` thread-local to match the MT-safe field library |

---

## 1. Parallelize the simulation (`f14cd63`)

**What changed - `ECRS.cc`**

- The run manager (created via `G4RunManagerFactory`) is now explicitly
  configured for **event-level multithreading**. When Geant4 is built with
  multithreading support this yields a `G4MTRunManager`; otherwise it falls
  back to a sequential run manager and the change is a harmless no-op.
- The **number of worker threads** is now wired up: an optional 3rd
  command-line argument sets it, defaulting to all available CPU cores.

  ```
  ./ECRS <seedIndex> <macroFile> [nThreads]
  ```

- The argument handling and `PrintUsage()` message were updated accordingly.
- All edits are commented with the date (9/25/2026) and rationale.

**Why this is safe / correct**

- The application was already structured for MT: `ECRSActionInitialization`
  implements both `BuildForMaster()` and `Build()`, and output uses
  `G4AnalysisManager`, whose per-thread ntuples are **merged automatically** by
  the master thread. Physics results are therefore unchanged.

**Expected performance gain**

Cosmic-ray showers are *embarrassingly parallel* (each primary event is
independent), so scaling is near-linear, governed by Amdahl's law
`speedup = 1 / (s + (1-s)/N)` with a small serial init fraction `s`:

| Physical cores | Realistic speedup (80-95% efficiency) |
|----------------|----------------------------------------|
| 4 | ~3.5-3.8x |
| 8 | ~6.5-7.5x |
| 16 | ~13-15x |
| 32 | ~25-30x |

Hyper-threads add only ~1.2-1.3x beyond physical cores; the one-time serial
initialization sets the ceiling for very short runs.

## 3. Thread-local field COMMON block (`6b760ba`)

**Background**

The magnetic-field library (`magnetocosmics/fortran/libFortranMagField.a`,
linked by this project) evaluates the field concurrently from multiple worker
threads in MT mode. Its per-call `COMMON` scratch blocks were made
`thread_local` in the `magnetocosmics` repository to make that race-free.

**What changed here - `include/magneto_fsubroutine_def.hh`**

- Declared `where_in_magnetopause2001__` as `extern thread_local` so its
  storage duration **agrees across translation units** with the field library.
- `bdip_` and the other `COMMON` structs remain shared (they are set once at
  configuration time and only read during tracking).

**Note**

This header is a shared copy that must stay in sync with the one in the
`magnetocosmics` repository. See `magnetocosmics/CHANGES_2026-09-25.md`,
section 3, for the full list of blocks that were made thread-local and the
rationale for leaving `bdip_`/`igrfcc_` shared.

## Recommended validation

Because the full Geant4 build could not be exercised in the environment where
these changes were prepared, run one end-to-end check on the target cluster:

1. Run a small job with `nThreads = 1`.
2. Run the same job (same seed index) with `nThreads = 4`.
3. Compare the ROOT output - they should match.

This confirms both the parallelization and the field thread-safety end-to-end.
